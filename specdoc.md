# LPQ Atlas — Authoritative End-to-End Completion Specification

**Project:** LPQ Atlas  
**Research title:** Dynamic Approximate Shortest Path Using a Learned Priority Queue  
**Document:** Authoritative implementation/completion specification  
**Status:** Final build specification  
**Primary rule:** Existing executable code is the source of truth. Documentation is evidence of intent, not proof of implementation.

---

## 1. Purpose

LPQ Atlas turns the existing shortest-path research repository into a complete, reproducible, interactive research application.

The existing project already contains a substantial C++ shortest-path/priority-queue engine, Python data/training/evaluation tooling, datasets, benchmark infrastructure, tests, experiment manifests, model artifacts, profiling and research notes. LPQ Atlas must preserve and finish that system rather than replace it with a web-demo rewrite.

The final system must allow a user to:

1. Select a real graph/dataset.
2. Select a real source and destination.
3. Run classical Dijkstra or A*.
4. Watch the actual search execution visually.
5. Inspect the exact shortest-path result and real execution metrics.
6. Run the same query using the Learned Priority Queue (LPQ).
7. Watch actual LPQ candidate selection, learned scoring, verification, correction/fallback and graph traversal.
8. Compare classical and LPQ executions using real measurements from the engine.
9. Run repeatable benchmark experiments across supported priority queues and datasets.
10. Inspect model, approximation and systems-level behaviour.
11. Reproduce research results from controlled experiment manifests.

No result displayed as an execution result may be invented, hard-coded or randomly generated.

# 3. Non-Negotiable Engineering Principles

## 3.1 The existing research engine remains authoritative

Do not reimplement Dijkstra, A*, LPQ, verification or the benchmark logic in JavaScript merely to support the frontend.

The existing C++ implementation remains the source of truth for algorithm execution.

Python remains the natural layer for the existing dataset, training, statistics and research tooling.

The web backend orchestrates these systems.

## 3.2 No fake visualization

The UI must never animate fabricated exploration.

Every visualized event must correspond to an event generated by a real algorithm execution.

Examples:

- node discovered,
- node pushed,
- node popped,
- node settled/finalized,
- edge relaxed,
- tentative distance changed,
- A* heuristic evaluated,
- LPQ candidate selected,
- learned score used,
- verification accepted,
- verification rejected,
- fallback triggered,
- correction performed,
- destination reached.

## 3.3 No fake metrics

Execution metrics must originate from the corresponding backend/C++ execution.

Never hard-code demo values for:

- runtime,
- path length,
- explored nodes,
- comparisons,
- pushes,
- pops,
- relaxations,
- candidate count,
- verification count,
- verification failures,
- fallback count,
- ML/scoring overhead,
- approximation ratio,
- phase timings.

Static examples may exist only in explicit documentation/demo fixtures and must never be presented as live experiment output.

## 3.4 Separate visualization timing from benchmark timing

Streaming thousands of events to a browser changes performance.

Therefore LPQ Atlas must distinguish:

### Visualization run
Instrumentation/tracing enabled. Used for teaching and replay.

### Benchmark run
Visualization tracing minimized/disabled. Used for trustworthy performance measurement.

Never report an animation-instrumented wall-clock measurement as though it were the clean benchmark runtime.

## 3.5 Preserve reproducibility

Every experiment must identify enough context to reproduce it:

- dataset,
- dataset version/snapshot,
- graph checksum,
- query/source/target,
- algorithm,
- priority queue,
- model/model checksum,
- correctness policy,
- epsilon,
- seed,
- relevant configuration,
- build/version/commit where available.

# 5. Documentation / Abstract / Code Discrepancy Register

This section is mandatory. Do not delete discrepancies merely to make documentation appear consistent.

## D-01 — OpenStreetMap promised but not fully implemented

### Claimed
The supplied abstract states that evaluation will use SNAP and OpenStreetMap datasets.

The original architecture/documentation also describes an OSM pipeline.

### Actual
The audited repository has meaningful DIMACS, SNAP and synthetic graph pipelines/artifacts. A complete OSM acquisition → road extraction → conversion → reproducible experiment pipeline equivalent to the existing dataset support was not found.

### Required LPQ Atlas resolution
Implement the OSM pipeline end-to-end.

Use free/public OSM data. Prefer reproducible `.osm.pbf` snapshots/region extracts for experiments rather than depending on live Overpass requests for large benchmark graphs.

Persist provenance:

- source,
- snapshot/download date,
- region,
- checksum,
- extraction/filter configuration,
- graph conversion version.

Convert OSM road topology into the existing graph representation rather than inventing a parallel graph engine.

---

## D-02 — “Online ML” wording is broader than the central experimental implementation

### Claimed
The abstract describes a lightweight online machine-learning model predicting the next node.

### Actual
The repository contains real online/adaptive infrastructure. However, the important optimized learned path also uses static graph features and precomputed per-node scores so that hot-path scoring can be an inexpensive lookup.

### Required resolution
Document both honestly:

1. **Static learned scorer mode** — precompute model-derived node scores and use them during execution.
2. **Adaptive/online facilities** — existing event/controller/learner mechanisms where enabled.

The UI must display the actual mode being executed.

Never show “online learning” if that run is using only precomputed scores.

---

## D-03 — Rich feature vision vs optimized feature path

### Claimed
Earlier architecture describes richer node, queue, search-state and graph-context features.

### Actual
The central optimized path relies substantially on static graph/node features because hot-path feature computation/inference can eliminate potential performance gains.

### Required resolution
Expose the actual feature/model configuration per run.

Future richer feature modes may be added, but they must be separately benchmarked and must not silently replace the existing optimized mode.

---

## D-04 — Model zoo vs selected experiment model

### Claimed/implied
Multiple model families are available.

### Actual
Multiple predictor implementations exist, but “implemented” does not mean every model is used in the primary experimental configuration.

### Required resolution
The Model page must distinguish:

- available model implementation,
- trained artifact available,
- active model for current run,
- benchmarked model,
- experimental/unused model.

---

## D-05 — Cache-miss/hardware counter metrics

### Claimed
The abstract lists cache misses among evaluation metrics.

### Actual
Hardware/PMU profiling was planned/supported conceptually, but the recorded WSL2 environment did not provide the required hardware counters for the intended measurements.

### Required resolution
LPQ Atlas must use capability detection.

Show hardware counters only when actually collected.

If unavailable, show:

`Unavailable on this execution environment`

Never show estimated/fabricated cache misses.

### Required resolution

## D-07 — Formal fuzzing

### Claimed
The testing strategy mentions fuzzing.

### Actual
Strong unit/differential/randomized testing exists, but a clearly established dedicated fuzzing system was not found.

### Required resolution
Add focused fuzz targets where valuable, especially around:

- graph binary parsing,
- model serialization/deserialization,
- queue operation sequences,
- approximation/correctness invariants,
- malformed experiment/config inputs.

Use an appropriate native fuzzing approach without compromising normal CI speed.

## D-08 — Packaged build portability

### Actual
The supplied ZIP contains generated Windows build artifacts and absolute Windows paths.

### Problem
Generated build state is not portable and caused Linux execution failures unrelated to algorithm correctness.

### Required resolution
Source repository must build cleanly from source.

Do not rely on checked-in platform-specific binaries/build directories.

Generated build directories should be excluded from the authoritative source distribution unless explicitly packaged as platform-specific release artifacts.

---

## D-09 — Expected positive outcome vs actual research findings

### Claimed
The abstract uses future/expected-outcome language suggesting the learned queue will offer efficient/scalable shortest-path computation.

### Actual
The experiments are more nuanced. Existing findings indicate that bucketing can provide major gains while LPQ candidate-window maintenance and verification can consume much of the saved work; trained scoring does not automatically produce end-to-end speedup.

### Required resolution
Do not manipulate LPQ Atlas presentation to imply LPQ always wins.

Comparison screens must display actual outcomes, including cases where:

- Radix Heap wins,
- Binary Heap wins,
- LPQ wins,
- LPQ reduces operations but increases runtime,
- approximation changes quality,
- model signal is weak.

Negative results are first-class research results.

---

## D-10 — Training/evaluation leakage history

### Actual
Research notes identify an earlier training/evaluation query overlap and subsequent disjoint evaluation.

### Required resolution
All LPQ Atlas research workflows must enforce or clearly report split provenance.

Training, validation and evaluation query sets must be identifiable and leakage checks should be automated where applicable.

# 8. Trace/Event Specification

A real visualizer requires an event stream generated by the actual execution.

Introduce a low-overhead observer/event sink around existing algorithm operations rather than contaminating core algorithm logic with frontend concerns.

Example event types:

```text
RUN_STARTED
SOURCE_INITIALIZED
NODE_DISCOVERED
QUEUE_PUSH
QUEUE_POP
NODE_SETTLED
EDGE_EXAMINED
EDGE_RELAXED
DISTANCE_UPDATED
ASTAR_HEURISTIC_EVALUATED

LPQ_BUCKET_SELECTED
LPQ_CANDIDATE_SELECTED
LPQ_SCORE_USED
LPQ_VERIFICATION_STARTED
LPQ_VERIFICATION_ACCEPTED
LPQ_VERIFICATION_REJECTED
LPQ_FALLBACK_STARTED
LPQ_CORRECTION_APPLIED

DESTINATION_REACHED
PATH_RECONSTRUCTED
RUN_COMPLETED
RUN_FAILED
```

Each event should contain only data needed for accurate replay.

Example conceptual event:

```json
{
  "schema_version": 1,
  "seq": 842,
  "type": "EDGE_RELAXED",
  "node": 431,
  "neighbor": 912,
  "old_distance": 1204.7,

```

```json
{
  "schema_version": 1,
  "seq": 1061,
  "type": "LPQ_VERIFICATION_REJECTED",
  "candidate_node": 912,
  "candidate_key": 1182.1,
  "score": 0.84,
  "reason": "candidate_not_safe_under_policy"
}
```

Actual field names must match the engine semantics.

Do not invent fields merely because they are visually attractive.

# 9. Trace Volume Strategy

Large graphs can generate millions of events.

The UI must not require transmitting every low-level operation for every run.

Support trace policies such as:

- `none` — benchmark mode,
- `summary`,
- `visual`,
- `full/debug`.

For large graphs:

- batch events,
- aggregate low-value repeated events,
- optionally sample visualization-only exploration events,
- always preserve final correctness/result metrics,
- preserve important LPQ decision events,
- clearly indicate when visualization uses aggregation.

The benchmark engine remains uninstrumented/minimally instrumented for timing comparisons.

# 10. OpenStreetMap Integration

## 10.1 Purpose

OSM serves two distinct roles:

1. Map visualization.
2. Real road-network graph source.

Do not confuse Leaflet/OSM tiles with the graph actually used by the algorithm.

A route drawn over OSM must come from nodes/edges in the processed OSM road graph.

## 10.2 Acquisition

Use free/public OSM extracts.

For reproducible benchmark datasets:

- download fixed regional `.osm.pbf` extracts,
- record provenance/checksum,
- do not rely on live API responses.

## 10.3 Road extraction

Define a documented road-access policy.

At minimum decide:

- drivable road types,
- one-way handling,
- prohibited/private roads,
- bridges/tunnels,
- disconnected components,
- duplicate/parallel ways,
- missing coordinates,
- turn restrictions if supported/not supported.

If turn restrictions are not implemented, document that limitation.

## 10.4 Graph mapping

Create deterministic mapping:

```text
OSM node/intersection
        ↓
internal graph node ID

OSM road segment
        ↓
directed/undirected weighted edge
```

Store coordinates for map rendering and A* heuristics.

## 10.5 Edge weights

Support at least distance-based routing.

Potential future/optional weight:

- estimated travel time.

Do not silently call a distance-weighted route “fastest route.”

## 10.6 Snapping

Map clicks rarely land exactly on graph nodes.

Implement:

```text
clicked lat/lon
      ↓
nearest eligible graph node
      ↓
show snapped point to user
```

The UI must distinguish the click from the snapped graph node where meaningful.

# 26. Performance Measurement Rules

## 26.1 Benchmark clock boundary

Define precisely what runtime includes.

Examples:

- graph already loaded vs graph-load included,
- model precomputation included/excluded,
- warmup,
- repeated queries,
- trace disabled,
- output serialization excluded/included.

Do not compare runtimes with different timing boundaries.

## 26.2 ML overhead

Separate when measurable:

- feature preparation,
- model scoring/precomputation,
- candidate maintenance,
- verification,
- fallback/correction,
- total LPQ queue time.

This is essential because existing findings show system overhead can dominate learned benefits.

## 26.3 Memory

Only show memory metrics if measured using a defined method.

Document platform differences.

# 27. Correctness Requirements

For exact mode:

```text
LPQ/reference distance equality
```

subject to the numeric tolerance appropriate to the weight representation.

For approximate mode:

```text
returned_distance / optimal_distance <= 1 + epsilon
```

where that is the actual policy guaranteed/validated by the implementation.

Every web-exposed algorithm configuration must preserve the same invariants as the underlying engine.

Add API/integration tests that run known graphs and compare web-returned results against direct engine results.
